# ADR-0025: Durable directed Relationships

Status: Accepted
Created: 2026-10-04
Accepted: 2026-10-04
Issue: [HV-22.4.5 / #80](https://github.com/mani8785/HomeVault/issues/80)

## Context

Evidence #79 is merged through PR #86. The next child of in-progress #72 is
durable Relationships. [ADR-0009](0009-asset-relationships.md) accepts a directed,
independent Relationship root, Covers kind, same-Vault endpoints, active-tuple
uniqueness and retained Removed state. [ADR-0022](0022-remaining-authorized-operations.md)
requires review of the exact API/schema before implementing this slice.

## Proposed contract

### 1. Vault-scoped create, inspect and remove

Base route: `/api/v1/vaults/{vaultId}/relationships`.

| Method and suffix | Input | Success |
| --- | --- | --- |
| POST (no suffix) | JSON `id`, `sourceAssetId`, `targetAssetId`, `kind` | 201 with Relationship metadata and Location |
| GET `/{relationshipId}` | No body | 200 with Relationship metadata |
| DELETE `/{relationshipId}` | No body | 204, including authorized repeated removal |

All identities are nonempty D-format Guids. The caller supplies a globally unique
Relationship id; `kind` is exactly `covers`. The intended Vault is in the route,
but both endpoint VaultIds are resolved from stored Assets and must equal it.
Even membership in both Vaults does not permit a cross-Vault link. Covers means
source insurance policy to covered target; Asset categories do not exist, so the
API does not pretend to validate those categories or create a reverse link.

Metadata contains `id`, `vaultId`, `sourceAssetId`, `targetAssetId`, `kind` and
`status` (`active` or `removed`). Location is the individual GET route. GET can
inspect Removed roots. DELETE changes only the Relationship status; neither
endpoint is deleted. Removed ids cannot be reused, but a new id may recreate the
same tuple after removal. No edit, reactivation, graph expansion, list/search,
cascade deletion or automatic retry is introduced.

Require authenticated cookies for all operations and antiforgery for writes.
Reject unknown JSON fields, requester identity fields and DELETE bodies. Current
members can read Active/Removed roots, including Archived Vaults. Writes require
Owner/Administrator/Editor on an Active Vault, including repeated removal.
Retain the host's request-size limit, no-store responses and safe problem format.

### 2. Retained roots and atomic active uniqueness

Add `Relationships` through a reviewed EF migration and separate configuration:

| Column | Storage rule |
| --- | --- |
| Id | Required TEXT Guid primary key, never generated by storage; nonempty check |
| VaultId | Required TEXT Guid; FK to Vaults.Id, restricted deletion |
| SourceAssetId | Required TEXT Guid; FK to Assets.Id, restricted deletion |
| TargetAssetId | Required TEXT Guid; FK to Assets.Id, restricted deletion |
| Kind | Required INTEGER; CHECK Kind = 0 (Covers) |
| Status | Required INTEGER; CHECK IN (0, 1), Active/Removed |

Add CHECK SourceAssetId <> TargetAssetId and a unique index on
`(VaultId, SourceAssetId, TargetAssetId, Kind)` filtered to `Status = 0`.
Reverse direction is a different tuple. Removed roots remain stored and reserve
their primary identities; they do not participate in active-tuple uniqueness.

Foreign keys enforce endpoint existence, not same-Vault ownership. The supported
adapter enforces actual ownership inside the write transaction; stored Asset
ownership is immutable in current supported operations. Validate ownership again
when reading/restoring Relationships; direct external SQL is not a supported
writer. Future Asset movement/deletion needs a separate reviewed policy rather
than bypassing these rules. Do not introduce redundant Asset keys for this slice.

The additive migration preserves all existing tables/data. Continue explicit
operator migration, known-history validation and verified backup/restore, with no
startup migration. No new package, script or framework dependency is proposed.

### 3. Narrow atomic Application contracts

Application owns create/inspect/remove contracts, immutable metadata and safe
outcomes. Read ICurrentActor once per call. Infrastructure acquires the existing
non-deferred SQLite write transaction before current membership, role, lifecycle,
endpoint ownership, conflicts and commit. Create invokes Relationship.Create;
removal uses an explicit validated restoration factory and Relationship.Remove.
No reflection, EF annotations, setters or loaded Asset graph enter Domain.

Restoration validates identities, kind, distinct endpoints and stored status
without replaying events; the adapter separately verifies actual stored endpoint
ownership. Invalid stored state fails safely without mutation. Persist only a new
Relationship row or its one-way status change, never either Asset or its components.

Inspect uses a consistent current-membership-scoped read transaction, verifies
the root belongs to the requested Vault and checks actual endpoint ownership
before returning metadata. It returns no Asset names, attributes or Evidence.
Archive, membership change, duplicate creation and removal must serialize with
Relationship writes. Keep the unique index as database enforcement in addition to
the adapter's safe conflict checks.

### 4. Failure order and disclosure

Authentication/antiforgery and transport shape/Guid parsing run first. Well-formed
writes then check requested Vault membership (404 `unavailable`), permitted role
(403 `forbidden`) and Active lifecycle (409 `vault_archived`).

For creation, resolve both endpoints in the requested Vault before kind/self-link
validation or conflicts. Missing endpoints, inaccessible endpoints and endpoints
in another Vault all share 404 `unavailable`, even when the requester belongs to
both Vaults. Then validate kind (400 `invalid_kind`) and self-reference (400
`self_reference`). Check identity conflict before active-tuple conflict. An existing
id in this Vault returns 409 `identity_conflict`; an id held by a different Vault
returns the same 404 `unavailable`. Active duplicate tuple returns 409
`relationship_exists`. No failure exposes another Vault's metadata.

Inspect/removal of missing or wrong-Vault roots share 404 `unavailable`. Removal
checks current role and archive before inspecting root conflicts/state; an already
Removed root succeeds only after those checks. Corrupt stored root/endpoint
ownership produces the existing safe 500 response for authorized access, never
partial state or raw provider exception text. Never log supplied references or
serialize Domain/storage entities as the transport contract. A failed HTTP response
does not prove no commit occurred.

## Alternatives and tradeoffs

- Physical deletion would lose the accepted lifecycle/history; retain Removed
  roots and use a filtered unique index to allow later tuple recreation.
- Checking duplicates outside the transaction permits competing successful
  creations. Atomic adapter checks plus database uniqueness enforce one active tuple.
- Trusting supplied Vault ids or merely checking membership in both Vaults permits
  forbidden cross-Vault links. Resolve both actual endpoint owners.
- Composite endpoint FKs could additionally enforce same-Vault ownership, but
  require extra keys/indexes on Assets. Existing immutable ownership plus atomic
  validation is the bounded choice; its database-only limitation is explicit.
- Generic CRUD or a graph library adds no needed capability. Existing EF Core,
  SQLite, ASP.NET authentication/antiforgery, approved guards and project results
  cover the slice without changing the accepted architecture.

## Implementation and evidence after approval

1. Add validated Relationship restoration, Application operations and contracts.
   Test trusted identity, preserved references/status, safe failures and repeated removal.
2. Add mapping/migration and SQLite adapters. Verify reverse tuples, removed-id
   conflicts, tuple recreation, all roles, endpoint isolation, rollback and retained
   Assets/attributes/Evidence. Test concurrent duplicates, removal/recreation,
   membership/archive races and invalid stored state with independent connections.
3. Add authenticated routes, OpenAPI and real-account/cookie tests, including
   cross-Vault endpoints for a shared member, antiforgery, spoofing, missing/
   inaccessible equivalence, current access and restart inspection.
4. Verify populated-schema upgrade and backup/restore preserve existing records
   plus Active/Removed roots. Document terminal backup/migration/startup/journey;
   review XML docs and run restore, format, Release build, NUnit, pending-model
   verification and current-revision Windows/Linux CI.
